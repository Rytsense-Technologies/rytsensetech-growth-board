COMPUTATION RULES:
1) GSC current = last 28 full days ending yesterday (UTC). Prior = the 28 days before that.
2) ctr is a percentage (e.g. 1.11), not a fraction. Round ctr to 2 decimals, position to 1 decimal.
3) change.clicks = current - prior; clicksPercent = ((current-prior)/prior)*100 if prior>0 else 0. Same for impressions. change.ctr / change.position = simple differences.
4) quickWins: position 4–15 AND impressions >= 100. opportunity = round(impressions * (1 - ctr/100) * 0.05 * (16 - position)). Sort opportunity desc; top 8.
5) GA4 = last 28 days through today. engagementRate = sessions-weighted average, 4 decimals. daily[].date = YYYYMMDD. channels = sessionDefaultChannelGroup, sessions desc.
6) github.recentCommits: up to 5; message = first line only.
7) CLOUDFLARE — analytics and deploy status are INDEPENDENT, and neither may be guessed.
   a) Analytics. NEVER write a numeric zero for a value you did not read. That is fabrication and it
      contradicts rule 3 at the top of this file. The old version of this rule said the status "may
      still be 'ok' … with analytics zeros"; the published file then carried requests /
      uniqueVisitors / threats / cacheHitRatio all = 0 under a green health dot, and a reader saw
      "this site received no traffic" when the API had simply never been called.
      If the Cloudflare Analytics API was not called, was blocked, or failed, write:
          "cloudflare": { "status": "unavailable", "analytics": null,

      Only when the API actually returned numbers: "status": "ok" with those numbers.
   b) Deploy status. Do NOT write cloudflare.deployment at all. You cannot know the outcome of a

      code after wrangler returns, and the Actions workflow commits it. Leave the existing

DEPLOY — ONE PATH ONLY:

The GitHub Actions workflow `.github/workflows/deploy-pages.yml` is the authoritative deploy. It
deploys git HEAD. Your job ends at the push.

1) Write data/latest.json via the file bridge (device_stage/commit or equivalent).
2) Also write history for today (see G above) the same way.
3) Run the validator (above).
4) Push ALL THREE files to GitHub via the GitHub API / github integration (Contents API
   create-or-update), preferably in ONE commit (Git Trees API) rather than three:
     - data/latest.json
     - data/history/YYYY-MM-DD.json
     - data/history/index.json
   Commit message: "chore: refresh dashboard data via Claude MCP"
   Branch: main (or the repo default).
   WHY one commit: on 2026-09-25 these were three separate Contents API calls 8 seconds apart
   (13:04:03 / 13:04:11 / 13:04:19). A run that dies between the first and the last leaves the
   history index without that day and the trend charts silently lose it — 2026-09-20 was lost this
   way. If you can only do three calls, push index.json LAST, and if the run dies partway, the next
   run must repair it: `node scripts/repair-history-index.mjs` (it derives the index from the
   snapshot files on disk).
5) That push triggers the deploy. Do not write cloudflare.deployment — see COMPUTATION RULE 7(b).

DO NOT ALSO RUN `npm run deploy:cf`.
This prompt used to instruct both paths on a good day. They deploy different sources — Actions
deploys git HEAD, the local script deploys the working tree with --commit-dirty=true — so whichever
finished last won. On 2026-09-25 the local tree held the full 500-row dataset, the push held 30
rows, Actions won, and the site served the truncated file for three days while the run reported
success. One path, always.

If the GitHub push itself fails twice: report the failure in the final reply, leave the repo alone,
and do NOT fall back to a local deploy — a local deploy would publish a tree that no commit
describes, which is exactly how the two sources diverge. A human can run the manual path
(README → Deploying) after checking what is on disk.

Known issue (Sept 2025+ Windows): Claude device_bash often fails with Plan9/virtiofs mount errors
while file read/write still works. That is NOT a failed refresh — the GitHub API push is the whole
job. Note it and carry on.
